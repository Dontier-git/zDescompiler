Qué hace GuardX con tu archivo

Todo el proceso ocurre en memoria, dentro de tu navegador. No hay backend, ni cuentas, ni subida de datos.

PASO 01

Desempaqueta el ZIP

Lee el índice central del `.jar` y descomprime las entradas con la API nativa del navegador, sin librerías externas.

PASO 02

Lee el bytecode

Decodifica las instrucciones JVM de cada método (invoke*, getfield, LDC, new), resuelve referencias del constant pool y reconstruye el grafo de llamadas. Nada se ejecuta.

PASO 03

Puntúa el riesgo

Correlaciona comportamientos entre métodos (lectura de archivos + envío HTTP, descarga + carga de clases) y asigna severidad, confianza y evidencias verificables.

Motor de reglas

Qué señales busca GuardX

Análisis estático sobre las instrucciones reales del bytecode, sin ejecutar el plugin. Cada hallazgo indica la clase, el método, la API, el endpoint y la evidencia que lo respaldan.

Ejecución y persistencia

  • Runtime.exec / ProcessBuilder — lanzamiento de procesos externos, con la cadena de comando encontrada.
  • API de attach de la JVM — agentes e inyección en otros procesos.
  • Librerías nativas — `.dll`, `.so`, `.dylib` o ejecutables embebidos, con atribución a la clase que las carga.

Red y exfiltración

  • Webhooks de Discord, Telegram y Slack — con clase, método y endpoint exactos.
  • Dominios temporales — ngrok, transfer.sh, webhook.site y similares.
  • IP literales y sockets — conexiones directas, con la API que las abre.
  • Construcción dinámica — URLs inferidas a partir de fragmentos de cadena.

Ofuscación y carga dinámica

  • URLClassLoader / defineClass — carga de clases en tiempo de ejecución.
  • Descarga + carga — combinación de lectura de red y cargador de clases.
  • Cifrado y blobs Base64 — payloads empaquetados o cifrados.
  • Nombres de clase mínimos — indicio de ofuscadores comerciales, sin tratarlo como malicioso por sí solo.

Integridad del paquete

  • Zip-slip — rutas de escape (`../`) o absolutas dentro del JAR.
  • Claves y tokens expuestos — AWS, claves privadas, tokens de bot, con valores redactados.
  • JAR sin firma y duplicados — archivos sobrescritos o no verificables.
  • Dependencias sombreadas — las detecciones indican si pertenecen a una librería empaquetada.
Preguntas frecuentes

Antes de instalar, pregunta

¿Mis archivos se suben a algún servidor?

No. GuardX es una página estática: todo el análisis ocurre en la memoria del navegador con JavaScript, y el trabajo pesado se ejecuta en un Web Worker local cuando está disponible. Puedes desconectarte de Internet después de cargar la página y seguirá funcionando.

¿Esto reemplaza una auditoría profesional?

No. Es un análisis heurístico estático: detecta señales conocidas de riesgo, pero no demuestra que un plugin sea seguro. Para plugins críticos, revisa el código fuente y ejecuta el servidor en un entorno aislado.

¿Qué formatos acepta?

Archivos `.jar` y `.zip`. Funciona con plugins de Bukkit, Spigot, Paper, Purpur, Folia, BungeeCord y Velocity, y con mods de Forge, NeoForge, Fabric y Quilt. También analiza JARs genéricos.

¿Puede haber falsos positivos?

Sí. Un plugin legítimo puede usar reflexión, conexiones HTTP o ejecutar procesos para backups. Por eso cada hallazgo muestra su motivo, su nivel de confianza, la evidencia y una lista de posibles falsos positivos. La puntuación orienta, no sentencia: contrasta siempre con el origen del archivo.

¿Cómo atribuye GuardX una operación a una clase y un método?

Decodifica las instrucciones JVM y resuelve las referencias del constant pool. Una detección se atribuye a un método solo cuando existe una invocación, acceso a campo o carga de constante real en su bytecode. Las combinaciones (por ejemplo, leer archivos y enviarlos por HTTP) se validan con el grafo de llamadas, no con la simple presencia de una API.

¿Qué pasa con las librerías empaquetadas (shaded)?

GuardX analiza todas las clases del JAR, no solo el paquete principal. Cuando una detección pertenece a una dependencia, lo indica en la ubicación y añade una advertencia de falso positivo; además agrupa las ubicaciones para no repetir el mismo hallazgo por cada clase de la librería.

¿Qué significan los niveles de riesgo?

Crítico: señales claras de ejecución arbitraria o exfiltración. Alto: capacidades peligrosas que requieren justificación. Medio: patrones sospechosos o de ofuscación. Bajo: higiene del paquete y observaciones.

¿Puedo usar el informe en mi servidor?

Sí. El botón JSON descarga un informe con la puntuación, los metadatos, el hash SHA-256 del archivo y todos los hallazgos con su evidencia, listo para adjuntar en un ticket o revisión interna.
